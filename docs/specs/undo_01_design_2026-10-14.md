## Decided (product owner, 8–14 Oct 2026)

- History is stored with the working copy and survives a reload.
- Discard is undoable.
- The last 10 edits are kept.
- A step holds the changed blocks only, not the whole document.
- Inserting an image is an undoable act, added when graphics are built.

## What the code gives us

- **Every text change already reaches one place.** `MemoDocument` never edits the memo itself: each of its acts — `replace` (edit, table rows), `addParagraph`, `splitBlock`, `removeBlock`, the empty-block drop after `finish` — ends in `onChange(markdown)`. In `Memo.tsx` every `onChange` ends in `setDraft`. `accept`, `putBack` and `discard` are in `Memo.tsx` and also call `setDraft`. So the refactor is one function in `Memo.tsx` that every one of these goes through, not nine changes in two files.
- **Blocks are lossless.** `parseBlocks` partitions the text into blocks that each keep their source; `serializeBlocks` joins the sources with `"\n"` (`memodoc.ts:309`). Comparing the block sources before and after a change gives exactly the blocks that changed.
- **Block ids are positional** (`"b" + n`, renumbered on every parse). A step cannot name a block by id; it names a position.
- **An open block owns its content.** `Editable` writes its HTML once on opening and reads it out on every change (`MemoReader.tsx:218-266`). Text replaced under an open block is overwritten by that block's next commit.
- **The working copy is opaque to the server** (`app.py:1964`). A history inside it needs no API, route, database or Terraform change. The 4 MiB cap applies to the whole stored object.

## Proposal

### One step

```ts
type Step = {
  act: "edit" | "add" | "split" | "delete" | "drop-empty" | "row"
     | "accept" | "put-back" | "discard";      // "image" added with graphics
  at: number;          // index of the first changed block
  before: string[];    // block sources as they were
  after: string[];     // block sources as they became
  // Only the acts that change more than the text carry these, as they were:
  accepted_by?: Record<string, number[]>;      // accept, put-back, discard
  pending?: Record<string, number>;            // accept, discard
  prompts?: Record<string, string>;            // accept, discard
};
```

`at`, `before` and `after` come from the longest common head and tail of the two block-source lists. An edit to one paragraph is one block in each list.

### Recording

One function in `Memo.tsx`, `change(act, next)`, replaces direct `setDraft` / `setAcceptedBy` / `setRuns` calls for the acts above. It computes the step from the state as it stands, pushes it, and drops the oldest past 10. `MemoDocument.onChange` gains a second argument naming the act; its mutation logic is unchanged, and the commit timing fixed in #126 and #128 is not touched.

### Undoing

Pop the last step. Check that the blocks at `at` still equal `after`; replace them with `before`; restore `accepted_by`, `pending`, `prompts` where the step carries them. Undoing an accept puts the rewrite back as out (`{id, result: null}`); the existing poll settles it as done from `memo_rewrite`, so Accept and Discard reappear. If the check fails, nothing is changed, the history is cleared and the screen says so.

### Refused

- **While a block is open.** Undo is disabled with "Finish editing first". Closing the block for the person instead would commit it as a new step and undo that rather than what they meant.
- **While a rewrite is in flight.** Disabled with "Wait for the rewrite to finish". The backlog's stale-accept risk.

### Stored

Working copy `version: 2`, adding `history: Step[]`. A `version: 1` copy loads with an empty history. Before each write the screen drops the oldest steps until the copy fits under 4 MiB, so the text is always written even when history cannot be (backlog § Risks). A copy with history but no other change is still written: after Discard the copy holds the original text and one step, not `null`.

### Discard

One step whose `before` is the working text against the memo's own, plus prompts, accepted rewrites and runs. Share stays gated on `hasChanges`, not on history, so a discarded copy does not block sharing.

### Save

Saving ends the history with the working copy, as the server already clears it. A saved revision is undone by opening the previous memo, as today.

### Placement

An Undo control in the memo head beside Save, in both modes, shown whenever there is history. Its title names the act it will undo ("Undo: delete a block").

### Not undoable, and seen not to be

Typing a rewrite prompt (the textarea keeps the browser's own undo), showing sources, opening a passage, toggling modes.

## Questions to be answered before build

1. **What is one edit?** Typing commits after every 400 ms pause, so counting commits makes 10 edits about ten pauses of typing. Proposed: everything typed into one block between opening and closing it is one edit; structural acts (add, split, delete, rows, accept, put-back, discard) are one each.
2. **Redo.** Not in the backlog. Proposed: none in this pass.
3. **Discard's confirmation.** It now can be undone. Keep the confirm, or drop it?
4. **Ctrl+Z outside an open block.** Inside a block the browser's undo stays. Outside, should Ctrl+Z undo the last memo step, or only the button?
5. **Save ends the history.** Confirm, as above.

## Product owner answers, 14 Oct 2026

1. **One edit: accepted as proposed.** Everything typed into one block between opening and closing it is one edit; each structural act is one.
2. **Redo: none in this pass.** Added later if asked for.
3. **Discard's confirmation: kept.** Undoable is not low-stakes; it is still the most destructive single click.
4. **Ctrl+Z: button only.** No document-level Ctrl+Z binding; the browser's own undo inside an open block is untouched.
5. **Save ends the history: confirmed.**

**Status: designed, ON HOLD — not started.** No code is written against this design until the UX02 work list's order is clear. UNDO-01 is not to be built ahead of UX02.

## Not changed

API, routes, database, Terraform, `_WORKING_MAX_BYTES`, the memo record, `memo_rewrite`.

## Bearing on graphics

The image sweep (P4) must treat an image referenced from any step in any working copy's history as in use.

## Verification, when built

Walk the journey on the real domain: each of the nine acts, undone; undo after a reload; undo after Discard; undo refused with a block open and with a rewrite out; an undone accept reappearing for accept; a long memo near the cap keeping its text.


## Ctrl+Z binding — deferred, 14 Oct 2026

Answer 4 stands: button only in this pass. Binding Ctrl+Z (and Cmd+Z) is left for later, not refused. The analysis given: it ignores text fields, so it does not fight the browser's undo inside a block; the remaining risks are an undo nobody sees (a step off-screen) and no redo to recover a stray keystroke. If it is taken up, bind it together with scrolling to the restored block and naming what was undone, not alone.

## Amended 26 October 2026, at build (`feature/undo-01`)

Additions to the design above, made in the build and agreed by the product
owner. The text above is left as written.

1. **An API change after all.** "Not changed: API" above is corrected. After
   Discard the kept copy holds the memo's own text and its history, and the
   server read any kept copy as unsaved, so "Share a memo" greyed out a memo
   whose own Share button was offered. The screen now writes `unsaved` into
   the copy (`hasChanges`), and `_has_unsaved` in `lambda/api/app.py` reads
   it: `unsaved: false` is not unsaved work. A copy without the field (version
   1) counts as unsaved, as every copy did. Deployed by `terraform apply`
   (the API Lambda), not by merging.
2. **Discard carries an Update that is out.** Discard also ends an Update
   still running. Its step records `update_run`, so undoing a Discard brings
   the run back and its poll resumes. Not in the step type above.
3. **Typing that empties a paragraph removes it in the edit.** An emptied
   paragraph leaves no block, so the edit's own step takes it out and one
   undo restores it; `drop-empty` is recorded only for a block that survives
   empty. Not walked on screen: no such block was found on the memo walked.
